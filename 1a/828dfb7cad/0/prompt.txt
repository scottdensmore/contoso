## 2. `pb-8` — right value, and it does nothing on desktop

`pb-8` sets the band height only when content exceeds 288px, i.e. **360 through 1024**. From 1280 up, `min-h-80` wins and the geometry is byte-identical to the old `h-80`: 320px band, content ending at 232, 88px of empty image below. So the desktop hero is **unchanged by this commit** and cannot have become bottom-heavy. Nothing to fix there.

Where `pb-8` does apply, it gives 32px below the last line against `pt-12`'s 48px above the h1. Slightly tighter at the bottom than the top; visible in `hero-390.png` but defensible. If you want symmetry, `pb-12`.

The structural note is better than the value note: **the two ends of the same gutter are owned by different elements.** `pt-12` is on the `h1` inside the inner container; `pb-8` is on the outer full-bleed `Block`. `innerClassName` is `""` and doing nothing. `innerClassName="py-12"` with both removed would put the vertical rhythm in one place and stop the top padding from disappearing if the `h1` is ever restyled.

### Finding 1 — the guard's anchor is unasserted, so it can retarget itself silently

**`/home/scottdensmore/Developer/scottdensmore/contoso/apps/web/e2e/layout.spec.ts:128`** — `const heading = document.querySelector('h2')`

The traversal is correct (see below), but the contract it measures is "the first `h2` in the document", while the test name and comment claim "the first category heading". Nothing asserts those are the same node, and the walk terminates at whichever `h2` `querySelector` found — so if an `h2` is ever introduced anywhere above the category sections, the anchor moves up, the walk stops early, and the hero copy below the new anchor is never measured at all. ### Answers to what you asked

**1. Traversal.** Correct and terminating. `heading.compareDocumentPosition(node)` returns the position of `node` relative to `heading`, so `&amp; DOCUMENT_POSITION_PRECEDING` is "node comes before the heading" — the sense you intended. Verified in jsdom, including two edge cases: the heading's own text node yields `FOLLOWING | CONTAINED_BY` and breaks correctly, and a whitespace-only category name does not run away — the `continue` skips it and the next non-whitespace node (the description) breaks the loop. Termination is guaranteed independently by `walker.nextNode()` returning `null`. Ancestors would report `CONTAINS | PRECEDING`, but text nodes are never ancestors, so that path is unreachable. Zero-height rects are guarded; the missing-`h2` case fails loudly rather than passing. The one unguarded vacuous state is finding 1.

**2. Asserting against the first `h2`.** The *contract* is right — "these two do not collide" outlives any particular fix. The *selector* is what is under-specified; see finding 1. Note also the implied tolerance: the category `Block` carries `innerClassName="p-8"`, so the `h2`'s border-box top sits 32px below the section top. An overlap of up to ~32px paints into the next section and passes. That is a defensible reading of "collision" and it is what let the 834px case register as exactly 10px, but it is worth knowing the guard's floor is not zero.

**3. `min-h-80 pb-8`.** Right expression of the fix. `min-h-80` is a valid v4 utility (20rem, same as the old `h-80`), and under border-box sizing the `pb-8` is absorbed while the content is short, so desktop proportions are unchanged and the padding only materialises in exactly the wrapping case it exists for. The asymmetry with the `h1`'s `pt-12` is cosmetic and correctly filed as #162 rather than restructured here.

**4. `bg-cover bg-no-repeat` in this diff.** Correct call, and it lands squarely in the `AGENTS.md` carve-out rather than near it: `min-h-80` is what allows the band to exceed the image's 450px height, which is what would introduce the horizontal tile seam.
