## Findings

### 1. The error text fails WCAG AA contrast — 3.96:1 measured, 4.5:1 required (high; pre-existing colour, but this change is what makes it matter)

Sampled from real rendered pixels of the `[role="alert"]` element, glyph core against the panel behind it:

| viewport | glyph | background | ratio |
|---|---|---|---|
| phone 390 | `rgb(231,0,11)` | `rgb(237,235,235)` | **4.02:1** |
| tablet 834 | `rgb(231,0,11)` | `rgb(235,234,233)` | **3.97:1** |
| desktop 1440 | `rgb(231,0,11)` | `rgb(234,234,233)` | **3.96:1** |

Best-case background pixel in any crop gave 4.23:1; worst-case 3.65:1. At 14 px / weight 500 this is normal text, so the threshold is 4.5:1. It fails everywhere.

The cause is not `text-red-600` alone — that colour is 4.77:1 on pure white and would pass. The panel is `bg-white/90 backdrop-blur-xs` sitting on `/images/contact-bg.webp`, so the effective background is ~`rgb(234,234,233)`, not white, and that 20-point drop is what pushes it under. Neither the colour nor the panel changed in this diff, so this is not a regression — but the whole point of #326 is making a failed submission perceivable, and it is currently not perceivable to the contrast standard.

Fix: `text-red-700` measures **5.33:1** against the same sampled background. One class, in `apps/web/src/components/contact-form.tsx`.

### 2. The #338 log does not fire on the case its own comment names (medium, not user-facing)

The `console.error` sits in `catch`, but an HTTP error response never reaches `catch` — `response.ok === false` takes the `else` branch, which calls `setError(data.message)` and logs nothing. Measured across three failure modes:

| injected failure | app logged? | message shown |
|---|---|---|
| network abort | yes — `TypeError: Failed to fetch` | "An unexpected error occurred…" |
| 500 with an HTML body (parse failure) | yes — `SyntaxError: Unexpected token '&lt;'` | "An unexpected error occurred…" |
| **500 with a JSON body** | **no** | "Server said no" |

The comment says the log is "the only place the actual failure survives: without it a network failure, a parse failure and a 500 are indistinguishable afterwards." The first two are covered; the 500 is not. In the three-viewport runs the only console output on a mocked 500 was Chromium's own `Failed to load resource`, nothing from the app.

Either move the log so the `else` branch is covered too, or narrow the comment to say network and parse failures.

### 3. The scoping is right; the reason recorded for it is not reproducible on this build (medium — a comment that invites a future "simplification")

You asked me to confirm the announcer. It is not there in the form you described. Measured:

### 4. Focus is still on `&lt;body&gt;` for the whole in-flight window (low, partially inherent to the fix's approach)

With a 1.2 s delayed response, measured mid-flight: button label `"Sending..."`, `disabled: true`, `opacity: 0.5`, `aria-busy: null`, `document.activeElement === BODY`, region empty.
